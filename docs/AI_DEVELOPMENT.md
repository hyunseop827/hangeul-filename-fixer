# AI 활용 개발 기록

이 프로젝트는 **AI 코딩 도구를 적극적으로 활용해 만들었습니다.** v1.0.0은 OpenAI Codex, 2026-10-01 정리 작업은 Claude Code(Claude Opus 5.5), 앱을 Swift로 다시 만든 2026-10-02 작업(v2.0.0)은 Claude Code(Claude Fable 5.1)를 썼습니다.
사람이 문제를 정의하고 방향과 최종 판단을 맡았고, AI는 코드 작성·리뷰·테스트·문서 작업을 도왔습니다.
이 문서는 누가 무엇을 했는지, AI를 어떻게 썼고 결과를 어떻게 확인했는지 남기는 기록입니다.

## 2026-10-01 정리 작업은 이렇게 했습니다

요청은 "코드 리뷰 → 개선과 안 쓰는 라이브러리 정리 → 문서 업데이트 → AI 컨텍스트 문서 → Git 정리 점검"을 순서대로, 확실하게 검증하면서 하는 것이었습니다.

1. **리뷰**: 6개 관점(파일명 로직, Electron 보안, 화면·UX, 빌드·의존성, 문서 정확성, 단순화)마다 리뷰 에이전트를 돌리고, 나온 발견마다 서로 다른 관점의 검증 에이전트 2개(직접 재현 / 의도와 가치)가 반박을 시도했습니다. 마지막에 빠진 것을 찾는 에이전트를 한 번 더 돌렸습니다. 총 114건이 나왔고, 반영 여부와 이유는 [CODE_REVIEW_2026-10-01.md](CODE_REVIEW_2026-10-01.md)에 있습니다.
2. **수정**: [AGENTS.md](../AGENTS.md)의 "Rules that must hold"(반드시 지킬 것: 원본 수정 금지, 덮어쓰기 금지, NFC 확인)를 바꾸지 않는 범위에서 고쳤습니다.
3. **수정 검증**: 고친 코드를 다시 4개 관점으로 리뷰하고 반박 검증해서, 이 수정이 만든 회귀(읽기 전용 파일 복사 실패, Vite 새로고침 차단, 배포 앱 메뉴에서 확대/축소 누락, 개발 실행기가 Electron 비정상 종료를 성공으로 처리)와 드래그 경로가 항상 NFD로 들어오는 문제 등을 추가로 찾아 고쳤습니다. 테스트가 실제로 버그를 잡는지 코드를 일부러 망가뜨리는 변이 테스트 16종으로 확인했습니다.
4. **실행 검증**: 타입 검사, 단위 테스트, 실제 Electron 창을 띄워 버튼을 누르는 자동 점검, 개발 모드 실행, DMG 패키징 후 실행, HFS+·exFAT·FAT32 디스크 이미지 저장 테스트까지 돌렸습니다.
5. **문서**: README 스크린샷은 실제 앱 화면을 자동으로 캡처하고 macOS 창 테두리를 그려서 다시 만들었습니다.

## 2026-10-02 Swift 재작성은 이렇게 했습니다

목표는 "Electron 앱(v1.1.0)과 똑같이 동작하는 Swift 앱"이었습니다. 새 기능은 없습니다. 2026-10-01 저녁에 시작했고, 조율하는 에이전트가 결정을 설계 문서로 적은 뒤 단계마다 실험·구현·리뷰·수정 에이전트에게 일을 나눴습니다.

1. **실험 먼저**: 코드를 쓰기 전에, Swift와 Foundation이 파일 이름을 어떻게 다루는지와 복사에 쓰는 시스템 호출이 볼륨마다 어떻게 동작하는지를 실제로 쟀습니다(APFS, 대소문자 구분 APFS, HFS+, exFAT, FAT32 이미지). 결과가 설계를 바꿨습니다.
   - Foundation의 NFC 변환은 한글에서 JavaScript와 달랐습니다(Node와 비교한 1,835,327개 입력 중 11,681개). ICU 변환은 차이가 0개여서 그것을 씁니다.
   - `FileManager`와 `URL`은 NFC 이름을 NFD로 저장했습니다. 그래서 사본은 POSIX 호출로만 만듭니다.
   - `fcopyfile`이 quarantine 값을 스스로 다시 찍었습니다. 그래서 복사 순서를 내용 → quarantine → 권한으로 정했습니다.
2. **규칙과 복사 엔진**: 1.x TypeScript 테스트의 모든 경우를 Swift 테스트로 옮기면서 구현했습니다. 앱 화면보다 먼저 만들고 리뷰를 마쳤습니다.
3. **1.x 코드와 결과 비교**: 진짜 1.x TypeScript를 Node로 돌린 결과와 Swift 결과를 같은 입력으로 비교했습니다. 문자열은 UTF-8 바이트의 16진수로 주고받아서, NFC와 NFD를 같다고 하는 비교가 끼어들지 못하게 했습니다.
   - 순수 함수: 유니코드 스칼라 1,112,064개 전부에 25가지씩(약 2,780만 개 값), 그리고 만들어 낸 입력 19,535,359줄. 차이 0개.
   - 복사 계획(`makePlan`): 입력 180,000개(APFS, 대소문자 구분 APFS, HFS+). 차이 0개.
   - 실제 복사: APFS에서 14,951가지 경우를 양쪽으로 복사하고 폴더를 바이트 단위로 비교. 16가지만 달랐고 모두 의도한 차이입니다(sticky 비트를 가져가지 않는 것, `xattr` 명령이 글자로 넘기지 못하던 quarantine 값을 바이트 그대로 옮기는 것). HFS+ 이미지 1,624가지와 exFAT 이미지 955가지에서도 같은 종류의 차이뿐이었습니다.
4. **변이 테스트**: 코드를 일부러 망가뜨려 테스트가 잡는지 봤습니다. 복사 엔진은 61가지 중 48가지가 잡혔고, 남은 13가지 중 3가지는 동작이 같은 변이, 10가지는 테스트의 빈틈이어서 테스트를 추가했습니다(리뷰 뒤 Core 테스트는 92개에서 107개가 됐습니다). 앱 쪽은 첫 리뷰에서 화면 코드의 변이가 대부분 살아남았고(상세 화면 15가지 중 15가지), 화면을 실제로 읽고 누르는 테스트를 추가한 뒤 62가지가 모두 잡혔습니다.
5. **실제 볼륨**: 외장 드라이브 동작은 모의가 아니라 진짜 HFS+·exFAT 디스크 이미지로 확인하고, 그 테스트를 저장소에 넣었습니다(`VolumeTests.swift`, CI에서는 필수). FAT32는 실험과 문서 작업 때 손으로 확인했습니다.
6. **앱과 화면**: 빌드한 앱을 접근성 API로 조작해서 파일 선택 → 이름 바꾸기 → 사본 만들기를 끝까지 확인하고, 화면은 Electron 1.1.0과 같은 파일로 나란히 띄워 비교했습니다. README 스크린샷은 2.0.0 앱의 실제 창을 찍은 것입니다(`screencapture -l`). 사용자가 Mac을 쓰는 중이라 창을 앞으로 가져오지 않고 찍어서 제목 막대가 비활성 모양(회색 버튼)입니다. 파일을 고른 뒤의 화면은, 선택 창을 백그라운드에서 조작할 수 없어서 선택 창 대신 실행 인자로 경로를 받게 고친 임시 빌드(저장소에 없음)로 찍었습니다. 초록·빨간 박스는 캡처 위에 그렸습니다.
7. **빌드·릴리스 파이프라인**: 저장소를 복제한 연습용 폴더에서 돌렸습니다. `release-plan.mjs` 시나리오 30가지, 일부러 망가뜨린 DMG 18가지가 `verify-dmg.sh`에서 모두 걸리는지, 스크립트가 실패하거나 중단돼도 임시 폴더와 마운트가 남지 않는지 확인했습니다.
8. **리뷰와 수정**: 엔진은 3개 관점, 앱과 파이프라인은 5개 관점으로 리뷰했습니다. 수정 에이전트는 발견을 먼저 재현한 뒤 고쳤고, 재현되지 않거나 1.x 동작과 어긋나는 제안은 이유를 적고 반영하지 않았습니다.
9. **사람의 결정**: Swift 앱의 첫 화면을 본 사용자가 아래쪽의 큰 빈 공간을 없애라고 했고, 창 높이를 내용에 맞추도록 바꿨습니다. 1.x와 일부러 다르게 한 화면 배치는 이것 하나입니다.

이 문서를 쓴 날 기준으로 `./scripts/test.sh`는 Core 108개(그중 umask 테스트 1개는 따로 실행), 앱 81개 테스트가 통과합니다.

검증 중에 실수도 있었습니다. 사용자가 같은 Mac에서 일하는 동안 에이전트가 앱을 조작하다가 키 입력 하나를 다른 앱으로 보냈을 수 있고, 클립보드 내용을 바꿨습니다. 그 뒤로는 앱을 앞으로 가져오지 않고, 그 앱의 프로세스에만 접근성 API와 키 이벤트를 보내도록 규칙을 바꿨습니다.

### 확인하지 못한 것

- **Intel(x86_64) 실행**: 이 Mac에는 Rosetta가 없습니다. Intel 쪽은 빌드만 했고 한 번도 실행하지 못했습니다. CI의 x86_64 테스트와 실행 확인이 처음 돌려 보는 것이 됩니다.
- **macOS 12 ~ 26**: 모든 실험과 테스트는 macOS 27 한 대에서 했습니다. 최소 지원 버전인 macOS 12에서 실행해 본 적이 없고, ICU 변환이나 exFAT 동작이 옛 버전에서도 같은지 확인하지 못했습니다.
- **실제 CI 실행**: 새 워크플로는 GitHub에서 한 번도 돌지 않았습니다. CI가 쓰는 Xcode 26.x의 컴파일러(Swift 6.2 이상)로 빌드해 본 적도 없습니다(이 Mac은 Xcode 27, Swift 6.4이고, macOS 26 SDK로 빌드되는 것까지만 확인했습니다). 러너에서 볼륨 테스트, 창을 띄우는 실행 확인, 태그·릴리스·다시 받기가 되는지는 첫 실행에서 단계별로 확인해야 합니다. PR의 CI는 릴리스를 만들지 않으므로 거기서 먼저 봅니다.
- **VoiceOver와 한글 입력기**: 상태 문구를 VoiceOver에 알리는 것과 조합 중인 한글이 이름에 들어가는 것은 단위 테스트로만 확인했습니다. 실제로 듣거나 입력기로 쳐 보지는 않았습니다.
- **네트워크 볼륨**: 확인하지 못했습니다.
- **폴더 접근 허용 창**: 데스크탑·문서·다운로드 폴더(와 iCloud Drive)의 파일을 처음 다룰 때 macOS가 띄우는 "…폴더의 파일에 접근하려고 합니다" 창을 평소 사용 흐름에서 겪어 보지 못했습니다(확인에 쓴 파일은 `/tmp` 아래에 있었습니다). 앱은 원본이 있는 폴더의 목록을 읽고 기본으로 그 폴더에 사본을 만들기 때문에 이 창이 뜰 수 있습니다. `Info.plist`에는 이 창에 보일 용도 설명(`NS…FolderUsageDescription`)이 없습니다. 1.1.0도 같은 방식으로 폴더를 읽었습니다. 허용하지 않았을 때는 Core 테스트로만 확인했습니다(폴더를 읽지 못하면 경로의 이름을 쓰고, 쓰지 못하면 "이 저장 위치에 쓸 권한이 없습니다…"를 보여 줍니다).

### 1.1.0에 있었지만 2.0.0에 없는 것

창 크기처럼 정해서 바꾼 것이 아니라, 옮기지 않은 채로 남은 차이입니다. 넣을지 말지는 저장소 소유자가 정할 일입니다.

- **화면 확대/축소**: 1.1.0 배포 앱의 보기(View) 메뉴에는 실제 크기, 확대, 축소(⌘0, ⌘+, ⌘−)가 있었습니다. 2.0.0에는 보기 메뉴도, 내용을 확대하는 기능도 없습니다. (윈도우 메뉴의 "확대/축소"는 창 너비를 넓히는 다른 기능입니다.)
- **화면 글자 선택**: 1.1.0은 웹 화면이라 사본 이름, 저장 위치, 상태 문구를 마우스로 선택해 복사할 수 있었습니다. 2.0.0에서는 이름 입력 칸의 글자만 선택됩니다.

## 원칙

- AI가 만든 코드도 사람이 쓴 코드와 같은 기준으로 리뷰하고 테스트합니다.
- AI의 주장은 실행해서 확인합니다. 리뷰 결과도 다른 에이전트가 재현하거나 반박해 본 뒤에 반영합니다.
- 실제 메일·제출 사이트 테스트처럼 사람 계정과 환경이 필요한 확인은 사람이 합니다.
- 사용자 파일을 지키는 규칙(원본 수정 금지, 덮어쓰기 금지)은 AI가 임의로 바꾸지 않습니다.
